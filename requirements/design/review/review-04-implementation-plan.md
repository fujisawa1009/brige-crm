## ✅ 確認済み（網羅性・順序が妥当だった箇所）

1. **P3新規実装項目の主要部分はR5に集約されている。** クレカ決済連携本体（P3-1/2）・手書き署名（P3-3）・

   重説チェック・申込確認メール（P3-12/13）は04 R5本文（`04-rails-implementation-plan.md:78-84`）に明示されている。
2. **P4-1（レコードレベル参照制御）の前倒しは意図通り機能している。** 03決定録・01§8-5の「後付けは手戻り大」という
   指摘を受け、R1で `Pundit policy_scope` を導入し「以降の全エンティティで必須」と明記（`04:48`）。Laravel側の
   最大の負債の一つを最初期フェーズで解消する設計になっている。
3. **P4-2〜4（統合ビュー・一括更新・名寄せ）・ftlog系メンションはR6に、決済/契約はR5に、正しく分離されている。**

4. **決済の状態機械設計原則（unknown≠failed・mark/confirm分離・HMAC-SHA256・非保持非通過・突合）はR5に
   具体的に転記されている**（`04:80-81`）。`payment-integration.md` §4の設計原則との整合は良好（詳細は❓4節）。
5. **R0でのftlog RBAC全面移植・監査基盤・Pundit導入という「認可・認可・監査を最初のフェーズに前倒しする」方針

   「R2のスキーマ設計時点からマッピング整合を常時確認する」と明記し、後回しにしない配慮がある（ただし内容面の
   ギャップは⚠️7参照）。

### 2. ftlog移植群（P4-13〜17）の一部が漏れている — IP許可リスト

01§5は「ftlog移植群（メンション/メールOTP/ログイン履歴等、P4-13〜17）」と一括りにしているが、P4-17は
「**IP許可リスト**＋メールOTPによる条件付き二要素認証」（`development-plan.md:193`, `ftlog-port.md` §2）であり、
メールOTPとIP許可リストは別機構（AND判定。`ftlog-port.md:57-64`）。
04を確認すると、R0は「認証: Devise（User）+ ftlog式メールOTP + rack-attack + ログイン履歴」（`04:30`）と
メールOTP・ログイン履歴は明記しているが、**IP許可リストへの言及がR0にもR6にも一切ない**。
`ftlog-port.md` D-1（空リストは「全員OTP必須」に倒すフェイルセーフ）はセキュリティ上重要な設計判断であり、
実装フェーズの割当てが漏れると着手時に見落とされるリスクがある。

### 3. R2の業務ロジックにPunditスコープ適用の明示的な指示がない（順序自体に矛盾はないが記述が不十分）

R1は「Pundit policy_scope で『代理店=自代理店のみ・グループ=配下のみ』を全一覧・詳細に適用（P4-1先取り。
**以降の全エンティティで必須**）」（`04:48`）と宣言している。この宣言自体はR1完結の範囲（AgencyGroup/Agency/
SalesRepresentative/ContractCondition/User）に対する適用であり、R2で新設されるCustomer/Store/Orderへの
適用はR1時点ではまだ存在しないモデルに対する話なので、**フェーズ順序としての矛盾はない**。
しかし、R2本文（`04:52-60`）には「Punditスコープを適用する」という記述が一度も出てこず、「全エンティティで必須」
という約束は「リスク・注意」節の3番目（`04:104`「参照制御の全面適用：R1以降の全エンティティでpolicy_scope必須を
レビュー観点に」）でしか担保されていない。**R1で確立した設計原則がR2の完了条件（`04:16`「案件90フィールド・
ステータス管理」）に反映されておらず、レビュー観点止まりでR2自身の完了条件になっていない。** 実装順で見落とされる
リスクがある（R0のフェイルクローズ副作用リスク1と同種の構造的弱点）。

### 4. R5の完了条件が決済状態機械のテストを要求していない

`payment-integration.md` §6（P3-2-j）は「**省略しない**。タイムアウト・二重送信・改ざんは手動再現不可。
モック自動テストが唯一の手段」（`payment-integration.md:161-163`）と強く明記している。
04のR5概要表の完了条件は「決済サンドボックス疎通・**契約状態機械spec**」（`04:19`）であり、
契約状態機械のspecは要求しているが**決済状態機械（PaymentTransaction）のspec化が完了条件に含まれていない**。
R5本文にも「spec必須」の語は登場しない（grep結果、`04:103`のリスク節で「specで遷移表を固定」と触れるのみで
完了条件ではない）。01§7の負債T-1（契約・決済・業務ロジックのテスト不在）を踏まえると、決済側にこそ
テスト完了条件が必要であり、この点は契約状態機械とのバランスを欠いている。

### 5. 決済専用キュー・自動リトライ無効化の明記漏れ

`payment-integration.md` §4-2は「Horizon デフォルト再試行のまま決済ジョブを流すと二重課金を自動で起こす。
**決済専用キューで再試行無効化**」と名指しで警告している（`payment-integration.md:92-93`）。これはSolid Queue
移行後も同型のリスクとして残る（ジョブのretry設定はキュー基盤に依らず存在する）。04のR5本文は「二重送信防止」
という結果は書いているが（`04:80`）、**その実現手段としての「決済専用キュー＋リトライ無効化」という具体策への
言及がない**。P3-2-hとして独立タスク化されていたLaravel側の粒度が04では溶けてしまっている。

### 6. R1〜R6にテスト要求の記述密度がばらついている

04本文中「spec」「テスト」の出現箇所を突合すると、明示的なテスト要求があるのはR0（認可テストハーネス・
403 request spec）とR3（申込トランザクションrequest spec必須）のみで、**R1・R2・R4・R6には業務ロジックの
spec化を求める記述が一切ない**。特に：
- R2は自動採番の競合安全化（`04:58`）という並行処理バグを生みやすい実装を含むが、テスト要求なし。
- R6は`customer-merge-design.md`で設計されている顧客統合（`lockForUpdate`・TOCTOU再検証・ワンタイム消費・
  代理店またぎ検知など、`customer-merge-design.md` §1-2/§5 に列挙された高リスクな並行処理・セキュリティ要件）
  を含むが、R6本文（`04:86-90`）にテスト要求の言及が一切ない。
01§7・03§7が「決済状態機械・申込トランザクション・参照スコープのspecを必須化」と述べている範囲に
「顧客統合」「自動採番」は含まれておらず、T-1負債対策がR3・R0以外のフェーズに拡張されていない。

### 8. R0完了条件が10項目中の一部しか検証していない

R0の10項目（`04:27-40`）に対し、完了条件（`04:42`「ダッシュボード1画面がログイン→OTP→権限チェック→表示を
通過し、権限剥奪で403 request spec がグリーン」）が実際に検証するのは項目4（認証）・5（認可）・8（Current/
created_by）・9（テスト基盤の一部）のみで、以下は完了条件のどこにも掛かっていない:
- 項目2（Docker整備：pg16+pg_bigm・tailwind watch・worker(Solid Queue)・mailpit）— ダッシュボード1画面の
  表示だけでは、pg_bigm全文検索・Solid Queueジョブ・mailpit経由メール送信のいずれも動作確認されない
  （OTPメール送信を実装するなら暗黙にmailpit経由が通る可能性はあるが、完了条件の文言には明記がない）。
- 項目3（フロント基盤：Hotwire/Turbo/Stimulus/Tailwind + ftlogレイアウト流用）— 単一画面の表示は
  レイアウト・パーシャル資産の流用可否を十分に検証しない。
- 項目7（監査ログ：Auditable concern・TRACKED_FIELDS・差分記録）— ログイン・権限チェックというイベントが
  実際に監査ログへ記録されることを完了条件が明示的に要求していない。R0の5大要素（認証・認可・監査・Current・
  テスト基盤）のうち監査だけが検証対象から漏れている。
- 項目10（CI：rubocop/brakeman/bundler-audit/rspec/認可スキップ検出grep）— 機能テストとは別体系のため
  完了条件外でも実務上は許容できるが、「CIが回る」という概要表の記述（`04:14`）と、詳細節の完了条件が
  「request specがグリーン」のみである点に落差がある。

**提案**：完了条件に「ログイン・権限チェックイベントが監査ログ（activity_log等）に記録されていることをspecで
確認」を追加する。Docker各コンテナ・CI各ステップの疎通は別途「R0チェックリスト」として完了条件と切り分けて
明示するとよい（完了条件を肥大化させずに網羅性を担保できる）。
