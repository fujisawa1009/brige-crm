## 0. なぜ今始めるか（律速の理由）

- 掲示板42万件（bridge 77,981 ＋ bridge_plus 342,594）の投稿者・対応者は**手入力文字列**で、
  ユーザIDと紐づいていない（`08` §2・`09` C-3-3）。移行後に「誰の投稿か」を成立させるには
  文字列→新IDの対応表が必須。
- 機械マッチングだけでは閉じず、**人手確認 → 業務側レビュー → 再マッチング**の反復が要る。
  1周に業務側の待ち時間が入るため**リードタイムが長い**。移行リハーサル（release B-7）までに
  複数周回す必要があり、手順を先に固めて回し始めるのが本書の目的。
- Q-C（掲示板実装方針）・Q-移1（移行範囲）が未決でも、**名寄せ表は範囲判断と独立に先行できる**
  （どの範囲を移行するにせよ対応表は同じものを使う。全ユニーク文字列を対象に作れば手戻りなし）。
  → Rails版: Q-C は「掲示板4種→問い合わせ統合（決定D-11）」として R4 で実装済み、掲示板42万件は参照アーカイブ（04 R7）と決定済み。
  名寄せ表の独立性はそのまま有効。

## 1. 問題定義

### 1-1. 名寄せ対象（入力側の母集団）

掲示板CSV（bridge / bridge_plus、34列）の**人名系フィールド**に入る手入力文字列。

| フィールド | 意味（`08` §2） | 対象 |
|---|---|---|
| `contributor` / `f_contributor` / `n_contributor` | 投稿者・次回投稿者 | ✅ |
| `manager` / `f_manager` / `n_manager` | 対応者・次回対応者 | ✅ |
| `first_insert_manager` / `first_insert_f_manager` / `first_insert_n_manager` / `first_insert_n_contributor` | 初回投入時の値 | ✅（同じ表で解決） |
| `admin_id` | 管理者ID（数値IDの可能性） | △ — 手入力でなくIDなら名寄せ不要。ステップ①で実態確認 |

- **母集団の見積り方**: 42万行 × 上記10フィールドを縦に展開 → トリム後の**ユニーク文字列数**を数える。
  行数ではなく**ユニーク数が作業量を決める**（人名なので数百〜数千オーダーの見込み。
  実数はステップ①の抽出で確定し、本書 §7 の作業量見積りを更新する）。
- 同時に**頻度（出現回数）**を集計する。人名は強いロングテール分布になるのが通例
  （常連の社内担当者が上位を占め、一度きりの顧客名・誤記が裾に散る）。頻度が全工程の優先順位を決める。

### 1-2. 紐づけ先（出力側）

投稿者は「社内スタッフ／代理店の営業担当／顧客（掲載主）」が混在する。紐づけ先は1つでなく
**種別（target_type）＋ 新ID** の組で持つ。

| target_type | 紐づけ先（Rails版 `db/schema.rb`・全て UUID 主キー） | 照合に使う現行マスタ | 実装状況 |
|---|---|---|---|
| `staff`（社内） | `users.id`（社内ユーザ。移行で作成。Devise・`name` `email` 列） | 現行の管理者/スタッフ一覧（`admin_id` の実態確認と合わせて特定） | テーブル実装済み（R0） |
| `sales_rep`（代理店営業担当） | `sales_representatives.id`（`sales_rep_code` UNIQUE・`name`・`agency_id`） | 営業担当者一覧_bridge（109件・16列）＋ BP_all_resp（310件） | 実装済み（R1） |
| `customer`（顧客・掲載主） | `customers.id`（旧 `jasmin_customers`。`customer_number` UNIQUE・`name`。マイページログイン主体を兼ねる＝03 §8-2 D-補足） | 案件CSV（all_bridge 1,206／all_bridge_plus 2,092）の契約者名 | 実装済み（R2） |
| `agency`（代理店名義の投稿） | `agencies.id`（`agency_code` UNIQUE・`name`） | 代理店一覧_bridge（302件） | 実装済み（R1） |
| `unknown` | ダミー（→ §5） | — | 未実装（R7） |

> 補足: `sales_representatives` はログインユーザではない（別テーブル・Devise 対象外）。
> **Rails版の書き込み先（R4 実装済み `Inquiry` / `InquiryMessage`）**:
> - 投稿者は `inquiry_messages.created_by_id` / `inquiries.created_by_id`（`TracksUser` concern。**`users` への FK・NULL 可**）→ `staff` のみ FK で表現できる。
> - 対応者は `inquiries.first_responder_name` / `next_responder_name`（**自由文字列**・任意）→ 名寄せ結果ではなく原文をそのまま入れられる。
> - `sales_rep` / `customer` / `agency` を投稿者として FK 参照する列は **無い**（宛先側の `inquiry_message_recipients.recipient_type/recipient_id` は polymorphic だが「宛先」であり投稿者ではない）。
> → 名寄せ表は **target_type＋旧マスタキー＋新UUID の3点で持つ**方針を維持すれば、投稿者列を「`users` FK のまま＋原文保持」にするか「polymorphic な `poster_type/poster_id` に拡張」するかの R7 判断に依存せず表の作り直しは不要（この独立性が先行着手を可能にする）。
> どちらにするかは §5 と併せて R7 着手時に決める（要確認）。

### 1-3. 名寄せ表のスキーマ（1行=1ユニーク文字列）

| 列 | 内容 |
|---|---|
| `raw_string` | 元の手入力文字列（トリムのみ・原文保持） |
| `normalized` | 正規化後文字列（§2-②のルール適用後） |
| `frequency` | 42万件中の出現回数（全対象フィールド合算） |
| `match_stage` | exact / normalized / partial / manual / unresolved |
| `target_type` | staff / sales_rep / customer / agency / unknown |
| `target_legacy_key` | 現行マスタ側のキー（resp_cd 等） |
| `target_new_id` | 新UUID（新ID採番後の周回で埋める。それまで空） |
| `confidence` | high / mid / low（partial・manual は根拠を残す） |
| `decided_by` / `decided_at` | 人手確定の記録（機械なら `auto`） |
| `note` | 判断根拠（同姓の弁別理由等） |

**置き場所（pii-handling-rules §4-2 準拠・Rails版パス）**: `storage/private/etl/name-matching/` 配下（Rails 標準 `.gitignore` の `/storage/*` で追跡対象外）。
requirements/ には置かない。コミットしない。カットオーバー検収後に全削除（同 §4-1）。

## 2. 手順設計（反復ループ）

```
① 抽出 → ② 機械マッチング → ③ 人手確認リスト生成 → ④ 業務側レビュー → ⑤ 版確定
        ↑__________________________(レビュー結果を辞書に反映して次周)__________________________|
```

### ① ユニーク投稿者文字列の抽出（頻度順）

- 掲示板2CSVの対象10フィールド（§1-1）を縦展開し、`raw_string` ごとに頻度集計。
  頻度降順の一覧を `storage/private/etl/name-matching/` に出力（Ruby 標準 `csv` で読み書き。ActiveRecord は不要＝DB に個票を入れずに済む段階）。
- 同時に確認する実態3点（初回のみ）:
  - `admin_id` が数値IDか文字列か。IDなら該当投稿は名寄せ不要になり母集団が減る。
    さらに **admin_id と contributor が同居する行は機械マッチングの正解データ（教師）に使える**。
  - フィールド別の充足率（contributor 系と manager 系でどちらが主か）。
  - 頻度分布（上位何件で投稿量の何%を覆うか）→ §4 の打ち切り基準を実数で確定。
- CSV読込は `09` C-1 の検証ルール準拠（列数検証・RFC4180・文字コード判定）。

### ② 機械マッチング（段階適用。上の段階で当たったら終了）

照合相手 = §1-2 の現行マスタ4種の氏名（こちらにも同じ正規化を適用する）。

| 段階 | 内容 | confidence |
|---|---|---|
| 1. 完全一致 | `raw_string` == マスタ氏名 | high |
| 2. 正規化一致 | 下記の正規化ルール適用後に一致 | high |
| 3. 部分一致 | 正規化後の包含（例: 名寄せ側が「姓のみ」でマスタ姓と一致）。**候補が一意のときだけ**採用。同姓が複数マスタにいる場合は自動確定せず③へ回す。Rails版候補: マスタ側を一時テーブルに載せ PostgreSQL の **pg_trgm**（`similarity()` / `%` 演算子。標準 contrib）または **pg_bigm**（`db/Dockerfile` に同梱済み。日本語2-gram向き。`enable_extension` は未実行＝`db/schema.rb` は `plpgsql` のみ）で類似度上位N件を機械的に出す。採用は「一意かつ閾値以上」に限定 | mid |
| 4. 未一致 | ③の人手確認リストへ | — |

**正規化ルール（辞書は周回で育てる）**

1. Unicode NFKC 正規化（全半角・半角カナ→全角カナを一括吸収。`09` C-5 と同方針。Ruby: `String#unicode_normalize(:nfkc)`）
2. 空白の除去（全角・半角・連続空白。姓と名の間の空白揺れを吸収）
3. 敬称の除去: 末尾の「様」「さん」「氏」「殿」等（辞書化。周回で追加）
4. 所属プレフィクス/サフィクスの除去: `FT` 等の**社名・所属の略号**（例: `FT浅賀` → `浅賀`）。
   **除去した略号は捨てずに target_type のヒントとして保持**する（`FT` が社内を意味するなら
   staff 探索を優先する等）。略号辞書は①の頻度上位を目視して初周で起案し、④で業務側に意味を確認
5. 記号・括弧注記の分離: 「・」「（）内の注記」等（分離した注記は note へ）

### ③ 残りの人手確認リスト生成（頻度順・上位から）

- ②の未一致＋partial（confidence=mid）を**頻度降順**で並べ、機械が出せた候補
  （近い氏名の上位3件程度＋根拠）を添えた確認リストを生成する。
- **ロングテールの打ち切り基準（案。①の実分布で確定）**:
  - 主基準: **累積頻度カバレッジ 97%**（投稿件数ベース）に達したら以降は人手確認しない
  - 補助基準: **頻度 5回未満**の文字列は原則確認対象外（1〜2回出現は誤記・一見客が多く費用対効果が低い）
  - ただし裾でも「マスタと正規化一致した文字列」は機械確定を維持する（人手対象から外すだけで捨てない）
- リストも `storage/private/etl/name-matching/` 配下。**Notion/Slack/Drive 等へのアップロードは
  禁止**（pii-handling-rules §3-3。氏名実値を含むため）。レビューはローカルのファイル受け渡しで行う。

### ④ 業務側レビュー

- 依頼内容は3種に絞る: (a) 人手確認リストの確定（この文字列は誰か）、
  (b) 略号辞書の意味確認（`FT` は何の略か・他の略号）、(c) 同姓弁別の判断基準
  （在籍期間・担当商材で機械弁別できるか）。
- レビュー結果は `decided_by`／`note` に記録して表へ反映。**辞書（敬称・略号・別名）に還元**して
  次周の機械マッチング率を上げるのが反復の肝。
- 業務側の窓口・往復のSLA（何営業日で返すか）は開始前に発注元と合意する（→ §7 の前提）。

### ⑤ 表の版管理

- 版は `name-matching-v001.csv` 形式の連番＋日付で、同ディレクトリ内にファイルとして残す
  （**git 管理はしない**。PII を含む移行データのため。pii-handling-rules §4-2）。
- 各版に必ずサマリ（ユニーク数・stage別件数・カバレッジ%）を添える。**サマリ数値のみ**が
  requirements/ 側（本書の変更履歴や進捗報告）へ転記可能な情報。
- ETL（`09` §6）はカットオーバー時点の**確定版のみ**を参照する。どの版を使ったかを
  `legacy_migration_logs`（R7 で新設予定の移行ログテーブル。`09` §6-2）に記録する。

## 3. 実行環境（方針のみ・実装は本書のスコープ外。**未実装・R7**）

- **入出力はすべて `storage/private/etl/name-matching/` 配下**で完結させる
  （pii-handling-rules §2-2/§4-1/§4-2）。原資料CSVは `requirements/input/`（brige-crm には未作成・R7 で追加）または
  `private/36.ジャスミン資料/` から読む。中間・出力を他の場所（spec/・docs/ 等）に書かない。
- 抽出・マッチングスクリプトは **rake タスク**として本リポジトリに実装する方針
  （例: `lib/tasks/legacy.rake` に `legacy:extract_posters` / `legacy:match_posters`。単発の検証は `rails runner`）。
  ETL本体（`09` §6-2 Rails版の `legacy:migrate`）と同系統に置き、コード自体は PII を含まないため通常どおりコミット可。
  長時間走る周回処理（42万行×10列の縦展開・類似検索）は **Solid Queue ジョブ**（`app/jobs/legacy/*_job.rb`）に載せ、
  ワーカー（compose の `worker`）で実行する。CSV エクスポート基盤 `CsvExportJob` と同じ非同期パターン。
  **コードにサンプル値・実名をコメントとしても書かない**こと。
- データアクセスは **ActiveRecord**（`User` / `SalesRepresentative` / `Customer` / `Agency` のマスタ読み出し）と
  Ruby 標準 `csv`。DB は **PostgreSQL 16**（UUID 主キー・`gen_random_uuid()`）。類似検索を DB 側で行う場合は
  pg_trgm / pg_bigm を **開発DBのみ**で `enable_extension` して使い、本番スキーマ（`db/schema.rb`）への追加要否は
  R7 で判断する（名寄せ用途だけなら移行作業用の一時DBで完結させ、本番には持ち込まない選択が安全）。
- 実行ログ（`Rails.logger` / ジョブログ）に氏名実値を出さない（件数・stage・行番号のみ。pii-handling-rules §4-3）。
- 人手確認リストのレビューはローカル完結（§2-③）。外部AIサービスへの実値投入は禁止
  （ローカルの Claude Code 処理は可・成果物への個票残存が禁止。同 §3-3）。

## 4. 精度目標の考え方（Q-移2 への回答案）

前提: ユニーク文字列の全件人手確認は非現実的（ロングテールの1回きり出現に人手を割っても
移行品質はほぼ上がらない）。**「文字列数の何%」ではなく「投稿件数の何%が実IDに紐づくか」
（頻度カバレッジ）で目標を置く。**

| 案 | 目標 | 想定コスト | 評価 |
|---|---|---|---|
| A | 全ユニーク文字列を人手確認（カバレッジ≒100%） | 最大 | ❌ 非現実的。裾は誤記・退職者・一見客で確認不能なものが残る |
| B | **頻度カバレッジ 97%（投稿件数ベース）で人手確認を打ち切り** | 中 | ✅ **推奨**。人名の頻度分布では上位の少数文字列で大半を覆える見込み。残余3%は §5 のルールで受ける |
| C | 頻度カバレッジ 90%・機械マッチング中心 | 小 | △ 早いが「不明ユーザ」投稿が目につく量になり、移行後の業務の納得感を損なうリスク |

- **推奨 = B**。ただし 97% は仮置きで、①の実分布（上位N件のカバレッジ曲線）を見て
  「+1% に要する人手確認件数」が急増する屈曲点で確定し、決定者/業務側の合意を取る。
- 合格条件は `09` §7 V-6（名寄せ未一致レポート）に接続: リハーサル時に
  **未一致率（件数ベース）≤ 3%・かつ機械/人手確定分の誤紐づけ0件（サンプル抽検）**を合格とする。

## 5. 打ち切り後の残余の扱い（紐づけ不能投稿者のデフォルト）

| 案 | 内容 | 評価 |
|---|---|---|
| a | 単一ダミーユーザ「**移行ユーザ（不明）**」に全部集約 | ✅ 推奨の土台。FK が全件解決し V-3/V-5 が壊れない |
| b | 文字列ごとにダミーユーザを自動生成 | ❌ ユーザマスタがゴミ文字列で汚れる。誤記1回ごとに1ユーザは過剰 |
| c | 投稿者FKを NULL 許容にする | △ スキーマが「投稿者必須」を諦めることになる。Q-C の設計を歪める。**Rails版注記**: R4 実装の `inquiry_messages.created_by_id` / `inquiries.created_by_id` は **既に NULL 許容**（`TracksUser` 標準）。ただし「NULL＝投稿者不明」を運用上の意味に流用すると通常投稿（`Current.user` 不在の投入）と区別できないため、本書の推奨（a）は変えない |
| 共通 | **移行後の掲示板レコードに `legacy_poster_name`（元の手入力文字列）を必ず保持**する | ✅ 必須。紐づけ結果に関わらず原文を残す。**Rails版: `inquiries` / `inquiry_messages` に該当列は未実装（R7 でカラム追加）**。対応者は `first_responder_name` / `next_responder_name`（string）に原文を入れられる |

- **推奨 = a ＋ 共通**: 不明分は単一ダミーユーザに寄せ、表示は `legacy_poster_name` の原文を出す
  （画面上は現行と同じ見え方が保てるので、実害は「不明分が検索・集計でまとまらない」ことに限定される）。
- 移行後に業務側が正体を特定できた場合に備え、名寄せ表はカットオーバー検収まで保持し
  （その後 pii-handling-rules §4-2 により削除）、付け替えは通常の運用機能ではなく
  個別データメンテとして扱う。
- `legacy_poster_name` 列の追加は Q-C の掲示板テーブル設計への**本書からの要求事項**として申し送る。
  → Rails版: Q-C は R4 で `Inquiry` 統合として実装済みだが `legacy_poster_name` は未追加。**R7 の移行マイグレーション**（`inquiry_messages.legacy_poster_name` string、必要なら `inquiries` にも）として申し送る。
  併せて「移行ユーザ（不明）」ダミー `User` の作成（`is_active: false`・ログイン不可・ロール無し）を R7 のシード/タスクに含める。

## 6. スケジュール感（反復周回の見積り）

**1周の想定作業量**（ユニーク数が想定レンジ＝数百〜数千に収まる前提。①の実数で更新）:

| 工程 | 主体 | 目安 |
|---|---|---|
| ①抽出＋②機械マッチング | 開発（AI実行） | 0.5日（rake タスク初回実装は+1日） |
| ③人手確認リスト生成 | 開発 | 0.5日 |
| ④業務側レビュー | 発注元/業務 | **2〜5営業日（律速はここ。往復のSLA合意が前提）** |
| ⑤反映・版確定 | 開発 | 0.5日 |

→ **1周 ≒ 1〜1.5週間**（実作業は2日弱、大半は業務側の待ち）。

**リハーサル移行（B-7）までに最低3周**:

| 周 | 目的 | 完了目安 |
|---|---|---|
| 第1周 | 実態確認（ユニーク数・admin_id・頻度分布）＋機械マッチング初回＋略号辞書起案。**打ち切り基準（§4）を実数で確定** | 開始から1.5週 |
| 第2周 | 業務レビュー第1回の反映・辞書拡充・人手確認の主力消化 | 3週 |
| 第3周 | 残件確定・新UUID採番後の `target_new_id` 埋め・**リハーサル用確定版（v-RC）** | B-7 初回まで |
| 以降 | リハーサル V-6 の未一致レポートを見て微修正（各リハーサルに1周ずつ随伴） | B-9 まで |

> 逆算すると **B-7 初回の約1か月前には第1周を開始**している必要がある。
> 名寄せ表が律速3点に入っている理由はこの業務側往復のリードタイムであり、
> 手順（本書）の確定と①②のスクリプト着手を先行させることで待ち時間を吸収する。
