| payment-integration.md の原則 | ネットムーブ実仕様 |
|---|---|
| D-P3 非保持・非通過（カード情報を自システムに通さない） | ✅ **カード番号はネットムーブ側で保持**。自社は会員ID・ブランド・上下4桁・有効性結果のみ |

## 3. フロー

### 新方式（採用）

```
申込入力
  → CRM側で checkout 初期化POST（サーバ→ネットムーブ）
    → ネットムーブ決済画面へ遷移（顧客がカード入力）
      → 3Dセキュア（ネットムーブ側で自動）
        → 結果を ret_url へ返却
          → CRM側で申込更新（card_status, card_brand 等）
```

### 旧方式（現行・廃止対象）

```
申込入力 → ネットムーブの旧ページ（/cgi-bin/get_back.pl）へ遷移 → 顧客がカード入力
  → 与信 → 結果反映
```

> **新旧の違いはエンドポイントとパラメータ、および3Dセキュア対応の有無**。
> どちらもカード入力画面はネットムーブ側にあり、カード情報は自システムを通らない。

### 4-1. チェックコード（check_cd）

| 項目 | 内容 |
|---|---|
| アルゴリズム | HMAC-SHA256 |
| キー | 事前に共有済みの HMAC キー |
| データ | `jutyu_cd` と `sum_price` をカンマ連結（例: `SMPL-0000001,10000`） |
| 形式 | 16進小文字化し、先頭に `HM` を付与 |

```ruby
# Rails版（R5で実装予定・未実装）。旧Laravel実装メモの hash_hmac('sha256', ...) と等価。
# HMACキーは Rails credentials / 環境変数から取得し、値をログ・ドキュメントに書かない。
message  = "#{jutyu_cd},#{sum_price}"
check_cd = "HM" + OpenSSL::HMAC.hexdigest("SHA256", Base64.decode64(hmac_key), message)
```

> ⚠️ **ret_url 側の check_cd は生成データが異なる**：「受注コード、カードブランド、
> 受注金額総額を `,` で結合」（ガイド 5.1.4）。**送信時と検証時でロジックが違う**ため、
> 実装では別メソッドにすること。検証側の比較は `ActiveSupport::SecurityUtils.secure_compare`
> を用いる（タイミング攻撃対策。詳細は `../payment-integration.md`）。
>
> ※ ガイドのデータ例 `SMPL-0000001` は**ハイフンを含む**。§4-2 の桁数問題と関連。

### 4-3. 受注コードの桁数問題（未確定）

| 情報源 | 値 | 桁数 |
|---|---|---|
| ガイド 5.1.3 本文 | 「決済を一意に特定する**12桁**の文字列」 | 12 |
| ガイド 5.1.3 データ形式 | `[サイトコード or モールコード][数字7桁]` 例）`ABCD 0000001` | 4+7=**11** |
| ガイド 4.2.3 チェックコード例 | `SMPL-0000001` | 4+1+7=**12**（ハイフン込み） |
| 管理画面 実データ | `S084-6001864` | 4+1+7=**12**（ハイフン込み） |
| 社内実装メモ | `'S0840000001'` | **11**（ハイフンなし） |

> ガイド本文の「12桁」とチェックコード例・実データが整合する。
> 社内実装メモの11文字表記が誤りの可能性が高い。
> → **ネットムーブへ確認（依頼 D-1）**。確定するまで実装は12文字前提で進め、
> 　 Rails migration では `t.string :jutyu_cd, limit: 12`（`payment_transactions`。**R5 で作成・現時点は未作成**）とする。
> 　 04 R5 着手前チェックリスト **Q-37（jutyu_cd 桁数）** として管理中。
>
> ※ 実データ `S084-6001864` の下位7桁が `6001864` と大きい値である点も未解明。
> 　 単純連番ではない可能性がある（採番規則＝依頼 D-4）。
>

> 新CRMプロトタイプの会員詳細画面で **ネットムーブ会員ID＝`60001864`（数字8桁）**、

> 会員ID採番の新旧連続・`member-modify` 導線は **R5**（04 R5「ネットムーブ会員IDの引き継ぎ対応」）。

## 5-b. 実装上の細かい懸念（ガイド再読で洗い出し・2026-07-27）

読み直しで見つけた、見落としやすい実装リスク。**いずれも payment-integration / P3-2 に反映済み**。

| # | 懸念 | 内容と対策 |
|---|---|---|
| C-a | **ret_url の POST 戻りでセッションが切れる** | ret_url_type=POST は**外部サイト（ネットムーブ）からのクロスサイトPOST**。Rails 既定（`SameSite=Lax` の session cookie）でもセッションCookieが送られず「ログイン状態が消えた」ように見える。さらに CSRF トークンも無いため **ret_url 受け口のコントローラで `protect_from_forgery` を skip（`skip_forgery_protection`）する必要がある**（旧Laravel記述の VerifyCsrfToken except 相当）。対策：ret_url をセッション非依存で設計（`jutyu_cd` で取引を特定。ユーザー状態はDBから復元）。ret_url_type=GET / REDIRECT の採用も比較検討（REDIRECTは完了画面を経由しない）。R5 未実装 |
| C-b | **ret_url の check_cd 検証には「金額」が要る** | 検証用 check_cd は「受注コード,カードブランド,金額」で生成されるが、**戻りパラメータに金額は含まれない**。送信時に `payment_transactions.amount`（R5 で作成）を保存しておき、検証時にDBから引く（送信前レコード方式なら自然に満たせる。テスト観点に追加） |
| C-c | **cancel_url は署名なし** | cancel_url 戻りは check_cd がブランク＝**真正性を検証できない**。キャンセル戻りを根拠に状態を変えない（canceled への遷移はサーバ間確定または管理画面確認によってのみ） |
| C-d | **成功判定は「member_id 非ブランク ∧ check_cd 一致」** | ret_url に結果コードが無いため、会員登録の成否は member_id のブランク有無で判定するしかない（ガイド5.1.4「会員登録に失敗した場合はブランク」）。check_cd 検証と併用し、**両方満たさない限り captured/authorized にしない**（unknown 留置） |
| C-e | **expiration_date 未指定は「翌日」で失効** | checkout 即時遷移なら問題ないが、申込フローが日をまたぐ運用（メール経由の再開等）だと失効する。有効期限を明示指定し、失効時の再開導線（新規採番）を用意 |
| C-f | **ng-19：リクエスト同時実行数オーバー** | 同時実行数の上限は非公開。ng-19 は「リトライすれば通る」性質のエラーだが、決済は自動リトライ禁止（`../payment-integration.md` §4-2。Rails版では **Solid Queue の決済専用キュー＋自動リトライ無効化**で担保。04 R5）のため**手動再開に乗せる**。閾値は依頼 E-5 で確認 |
| C-g | **受注コード重複は ng-05（パラメータエラー）に混ざる** | 冪等キー衝突と単純な入力ミスが同じコードで返る。ログで区別できるよう、送信前に自社DBの unique 制約で弾く設計を維持（DB が第一防壁、ng-05 は最終防壁） |
| C-h | **決済画面カスタマイズはサイト単位で共通** | 決済画面設定は EC決済・会員登録・メールリンク決済の**全用途に共通適用**（ガイド2.3）。商材ごとに文言・ロゴを変えたければ**サイト分割が必須**になる公算大（論点10 の補強） |
| C-i | **3DSチャレンジ認証と高齢者顧客** | 申込書には高齢者同意書の枠があり（テストでも代表者85歳）、**カード会社のID/パスワード入力（チャレンジ認証）を高齢の契約者が突破できず決済不成立**が増えるリスク。認証情報（メール・電話）を多く送るほどフリクションレスになりやすい＝§4-5 の項目をできる限り埋める実装が実質的な対策。D-P5（失敗時ハンドリング）の主要ケースとして想定しておく |
| C-j | **SMS送信用携帯番号が既にある** | 会員詳細に「SMS送信用携帯番号」フィールドが存在し、申込書にも SMS送信サービス利用規約への同意がある。**3DS用の `cardholder_info_mobile_phone_*` にこの番号を転用できる**（新規取得不要）。brige-crm では `customers.sms_mobile_number`（R2 実装済み）が対応 |
| C-k | **旧APIは Shift-JIS** | 旧 get_back.pl の応答は `text/html;charset=Shift-JIS`（キャプチャのヘッダで確認）。新APIは UTF-8。**移行期に新旧を並行運用する場合、文字コード処理を混在させない** |
| C-l | **与信の有効期限が未記載** | 一般にカード与信（オーソリ）には有効期限がある。「与信済み」の取引を後日売上化できる期間、および1円与信の取消猶予は**ガイドに記載なし** → 依頼 A-8 |
| C-m | **おまとめ請求は申込書に既にある** | 契約申込書のお支払方法欄は「□口座振替 ■クレジットカード □**おまとめ請求【おまとめ先案件番号】**」の3択＋会員詳細に「合算請求希望」フィールドあり。`business-flow-analysis` の「bundled_billing は契約後スタッフ入力」という整理と**矛盾する実物**であり、論点1（判定タイミング）は**申込書ベースで解決できる可能性**（社内 S-4 の材料）。brige-crm では `orders.payment_method` / `orders.bundled_billing` / `orders.bundle_target_order_number` / `customers.consolidated_billing`（R2 実装済み）が受け皿 |
| C-n | **おまとめ請求「する」は441件（21%）** | 例外ではなく主要フロー。論点13（N案件:1決済の紐づけ単位）の優先度を上げる根拠 |
