## 0. 結論：現行データは「そのまま入らない」。整形が必須。

現行CSVを精査した結果、**新スキーマへ機械的に流し込めない**問題が複数見つかった。
データ移行は「コピー」ではなく「**ETL（抽出→整形→検証→投入）**」として設計する。

| 整形課題 | 深刻度 | 影響 |
|---|---|---|
| C-1 CSVの破損（列数不一致） | 🔴 高 | パース自体が失敗する |
| C-2 分割カラムの結合（住所・電話・営業時間） | 🔴 高 | 新スキーマの1カラムに複数列を結合 |
| C-3 掲示板の横持ち→縦持ち正規化 | 🔴 高 | 4種ステータスが1行に横持ち。42万件 |
| C-4 コード値の名称変換（prefecture_id 等） | 🟠 中 | 数値コード→表示値 |
| C-5 表記ゆれ・半角カナ・名寄せの正規化 | 🟠 中 | 名寄せ・検索の精度 |
| C-6 ステータスの旧→新マッピング（統廃合） | 🟠 中 | `03` の統廃合を適用 |
| C-7 文字コード | 🟠 中 | **CSVごとに異なる**（DB退避=UTF-8／案件CSV=CP932）。読込時に判定・統一が必要 |

## 1. C-1：CSVの破損（列数不一致）— 最優先

**全CSVの列数を検証した結果、2種類の破損を検出した。**

| CSV | ヘッダ列 | データ列 | 判定 |
|---|---|---|---|
| グループ一覧_bridge | 6 | 6（36件） | ✅ |
| 代理店一覧_bridge | 19 | 19（302件） | ✅ |
| **営業担当者一覧_bridge** | 13 | **16**（109件） | 🔴 **ヘッダ破損** |
| 施工担当者一覧_bridge | 3 | 3（36件） | ✅ |
| 店舗一覧_bridge | 24 | 24（1,247件） | ✅ |
| **店舗一覧_bridge_plus** | 24 | 24（2,178件）＋**47列が1件** | 🔴 **データ行破損** |

### C-1a：ヘッダの破損（営業担当者）

ヘッダのカラム名が連結（区切りカンマの欠落）。ヘッダ13列だがデータは16列で一貫。
```
… resp_shop_address_2resp_shop_address_3 …   ← address_2 と address_3 が連結
… resp_shop_tel_1resp_shop_tel_2 …           ← tel_1 と tel_2 が連結
… resp_shop_tel_3resp_shop_fax_1 …           ← tel_3 と fax_1 が連結
```
→ **ヘッダを信用せず**、データ側16列を正としてカラム定義を人手で復元する。

### C-1b：データ行の破損（店舗 BridgePlus）

**2,178行は24列なのに、1行だけ47列**に暴走している。
典型的な**フィールド内カンマ（住所や施設名に「,」）のクォート漏れ**、または
**フィールド内改行**によるレコード分割の失敗。

→ **1件でも混ざると以降の行が全てズレる危険**。列数が期待値と違う行は
**投入せず要目視リストへ隔離**し、元データ（現行DB）から正しい値を取り直す。

**整形ルール C-1**
- ヘッダは破棄し**列定義を別途マスタ化**（CSVヘッダに依存しない）
- **全行**について `列数 == 期待列数` を投入前に検証。**不一致行は隔離**（サイレントに詰めない）
- CSVパーサはRFC4180準拠（クォート内カンマ・改行を正しく扱う）で読む
- **文字コードをCSVごとに判定**（案件CSVはCP932、DB退避はUTF-8）。末尾の空列（トレーリングカンマ）は無視
- できれば**CSV経由ではなく現行DBから直接エクスポートし直す**方が安全（破損・文字コード差の根治）

## 2. C-2：分割カラムの結合

現行は住所・電話・営業時間を**細切れの列**で持つ。新スキーマは統合形。

### 店舗（`facility_*`）の分割列

| 現行の分割列 | 新カラム（`stores`。R2 実装済み） | 結合ルール |
|---|---|---|
| `post_1` + `post_2` | 郵便番号 | `post_1`-`post_2`（7桁化） |
| `prefecture_id` + `address_1/2/3` | 住所 | 都道府県コード→名称＋以降を結合 |
| `tel_1` + `tel_2` + `tel_3` | 電話番号 | `-` 連結 |
| `fax_1` + `fax_2` + `fax_3` | FAX | `-` 連結 |
| `space_open_time` + `space_open_time_min` | 営業時間1（開始） | `HH:MM` 化 |
| `space_close_time` + `space_close_time_min` | 営業時間1（終了） | `HH:MM` 化 |
| `space_open_time2` … `space_close_time2_min` | 営業時間2 | 同上（2枠目） |
| `space_regular_holiday` | 定休日 | そのまま |

**整形ルール C-2**
- 時刻は「時」「分」が別列 → `sprintf('%02d:%02d')`。空なら NULL
- 電話は現行が3分割。新は1カラム → ハイフン結合。桁バリデーション
- 郵便番号は `post_1`(3桁)+`post_2`(4桁)

### 営業担当者（`resp_shop_*`）も同様に分割 → 結合

`sales_representatives` の `pdf_*`（PDF出力用住所）へ。post/address/tel/fax を結合。

## 3. C-3：掲示板の横持ち→縦持ち正規化（最大の作業）

現行掲示板は**1レコードに4種のステータスを横持ち**（`legacy-research/05` の4掲示板が1テーブル）。

### 整形ルール C-3

1. **掲示板種別を判定して縦持ちに分解**：`bbs_status` / `bbs_after_status` /
   `bbs_ac_call_status` の**どれに値が入っているか**で「後確／制作／アフター／検収コール」を判別し、
   新スキーマの「掲示板種別」列に振り分ける（Rails版: `inquiries.category`（後確/制作対応/検収コール/アフター問合せ）＋ `inquiries.status`（`inquiry_statuses` マスタ）。R4 実装済み。`10` §6）。
2. **スレッド構造**：`parent_bbs_id` で親子（返信）を復元。`latest_flg` で最新版判定。
3. **対応者マッピング**：`manager`/`contributor`/`n_manager` を新システムのユーザ（社内/代理店/顧客）へ
   名寄せ。**現行は投稿者名が手入力文字列**（`FT浅賀` 等）でユーザIDと紐づいていない
   → **完全一致しない可能性が高い**。名寄せ表が必要（C-5と連動）。
4. **本文のクレンジング**：改行・文字数（現行は2000字上限で分割投稿）。分割投稿の再構成方針。
5. **移行範囲の判断**（Q-C 連動）：42万件全件 or 直近N年 or アーカイブ別テーブル。
   **性能上、全件を本番テーブルに入れるとスレッド表示が重くなる**懸念。

> **掲示板が移行の最大コスト**。Q-C（掲示板の実装方針）が決まらないと C-3 の設計が固まらない。
> **Q-C を先に決める**のがデータ移行の律速。
> → Rails版: Q-C は「掲示板4種→問い合わせ統合（決定D-11。R4 実装済み）」＋「42万件は参照アーカイブ（04 R7）」で決着。C-3 の設計は `10` §6 の対応表で固められる。名寄せ（3.）は `../name-matching-process.md`（R7）。

## 5. C-5：表記ゆれ・名寄せの正規化

| 対象 | 問題 | 整形 |
|---|---|---|
| グループ・代理店名 | 半角カナ（`NEXTﾊﾟｰﾄﾅｰ`）・全半角混在 | 全角正規化・トリム |
| 会社名フリガナ | 合同会社→カブシキガイシャ等の誤り（現行不備） | 移行時に検知・フラグ立て（自動修正はしない） |
| 掲示板の投稿者（`FT浅賀`等） | ユーザIDと未紐づけ（手入力文字列） | **名寄せ表**（表記→ユーザID）を作成。未一致は「不明ユーザ」で保持 |
| メールアドレス（`;`区切り複数） | 店舗メール複数入り | 分割して正規化 |

> **自動修正はしない方針**：フリガナ誤り等は「検知してフラグを立て、目視判断」。
> 勝手に直すと元データとの追跡性を失う。移行ログに残す。

## 6. ETLの実装方針

### 6-1. 処理構成

```
[抽出] CSV読込（UTF-8・列数検証）
  → [整形] 結合・変換・正規化・名寄せ（本書のC-1〜C-6）
    → [検証] 件数・必須・関連（FK）・金額の突合
      → [投入] チャンク単位でDB投入（トランザクション）
        → [レポート] 変換ログ・未一致・要目視リストを出力
```

### 6-2. 実装手段

| 手段（Rails版・2026-08-19。**いずれも未実装＝R7**） | 用途 |
|---|---|
| rake タスク（`lib/tasks/legacy.rake`: `legacy:migrate[entity]` 等）／単発検証は `rails runner` | ETL本体。Ruby 標準 `csv`（RFC4180・`encoding: "CP932:UTF-8"` 指定で C-7 を吸収）＋ ActiveRecord。既存の CSV 基盤（`CsvExport` / `CsvExportJob`）と同じ非同期パターン |
| チャンク処理 | 掲示板42万件は `CSV.foreach` のストリーム読み＋ `each_slice(500)`／`insert_all`・`upsert_all`。**暗号化列（`order_work_details` のアカウント8列・`orders.billing_password`）は `encrypts` を通すため必ずモデル経由（`create!`/`update!`）で投入**（`insert_all` は暗号化を通らない） |
| 専用キュー | Solid Queue の専用キュー（例 `legacy_migration`）＋ compose の `worker` で非同期。決済専用キューとは分ける |
| ドライラン | `DRY_RUN=1`（環境変数 or タスク引数）で投入せず検証レポートのみ（本番前の必須ステップ）。トランザクションを開いて最後に `raise ActiveRecord::Rollback` する方式も可 |
| 変換ログ | `legacy_migration_logs` テーブル（旧ID→新ID対応・変換内容・警告。R7 で新設。`inquiries` 等に旧ID列が無いため必須＝`10` §6） |
| 監査ログ | 移行投入は `Auditable` concern により `audit_logs` に大量記録される。移行実行時のみ監査記録を抑止するか、`Current.user` を「移行ユーザ」に固定して残すかを R7 で決める（要確認） |
| 採番 | `customer_number` / `order_number` / `inquiry_number` は旧値を保持して投入し、`sequence_counters` を旧最大値まで繰り上げる（`SequenceCounter`。R2 実装済み） |

### 6-3. 冪等性・再実行

- 移行は**リハーサルを繰り返す**（B-7）。**何度流しても同じ結果**になるよう、
  旧ID（`bbs_id`・`l_store_place_cd`・`resp_id` 等）を新レコードに保持し、
  `find_or_initialize_by(旧ID)` / `upsert_all(unique_by:)` で再実行可能にする（Rails版。業務CD（`group_code` `agency_code` `sales_rep_code` `store_code` `customer_number` `order_number`）は実カラムに保持できるが、`bbs_id` の受け皿は無いため `legacy_migration_logs` で対応づける）。
- 旧ID保持は**移行後の照合（reconciliation）**にも使う。

## 7. 検証（投入後の突合）

| # | 検証 | 合格条件 |
|---|---|---|
| V-1 | 件数突合 | 旧CSV件数 == 新レコード数（除外分は明示ログ） |
| V-2 | 必須項目 | 案件番号・顧客番号・代理店CD が全件埋まる |
| V-3 | 関連（FK） | 案件→顧客→代理店→グループ の参照が全て解決 |
| V-4 | ステータス | 旧→新マッピング後、未定義ステータスが0件 |
| V-5 | 掲示板スレッド | `parent_bbs_id` の親が全て存在（孤児0件） |
| V-6 | 名寄せ未一致 | 投稿者・対応者の未一致件数をレポート（0が理想、要目視） |
| V-7 | 金額・プラン | プラン→月額が旧と一致 |
