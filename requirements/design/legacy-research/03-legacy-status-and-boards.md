## 1. 掲示板は4種類（重要な訂正）

`business-flow-analysis.md` §4 では掲示板を「3種」としたが、**正しくは4種**。

| 掲示板 | 用途 | 選択可能ステータス |
|---|---|---|
| 後確掲示板 | 不備チェック・確認コールの連絡 | 対応中 / 営業部対応依頼 / 営業部対応中 / 後確依頼 / 後確NG / 再申請 / 後確OK / キャンセル |
| 制作対応掲示板 | 作業進行中の対応依頼・進捗・共有 | 制作対応中 / FT確認依頼 / 営業部対応依頼 / 営業部対応中 / 再申請 / 制作OK / キャンセル |
| 検収コール掲示板 | 納品チェック完了・検収コールNG | 検収コール対応中 / 検収コールNG / 検収コールNG対応中 / 再申請 / 検収コールOK / キャンセル |
| **アフター掲示板** | **納品後の解約共有・アフターフォロー** | 未対応 / 対応中 / 対応済 / 完了 |

> **アフター掲示板**は解約処理待ちステータスで「営業担当宛に解約共有」に使われる（§2 参照）。
> `business-flow-analysis.md` の掲示板記述に本項を追記する必要あり。

### 掲示板の設計示唆（新システム）

- 各掲示板は**ステータス駆動**で、ステータス選択が通知トリガー
- 掲示板ごとにステータス集合が異なる → **掲示板種別 × ステータスのマスタ**が必要
- 「営業部対応依頼 / 営業部対応中」など**通知目的のステータス**が混在
  → 「通知の要否とステータスを分離」方針で整理する（旧出典 `ftlog-port.md` は 2026-08-19 削除済み。
  　 Rails 版の一次情報は `../board-implementation-options.md`（決定 D-11）と R4 実装）

**brige-crm 実装状況（R4 実装済み・2026-08-19 突合）**: 掲示板4種は独立実装せず `Inquiry` に統合した
（決定 D-11・`../board-implementation-options.md` 推奨案①）。

| 本節の概念 | brige-crm の実装 |
|---|---|
| 掲示板4種 | `Inquiry::CATEGORIES` = 後確 / 制作対応 / 検収コール / アフター問合せ（`inquiries.category`） |
| 掲示板種別×ステータスのマスタ | `InquiryStatus`（`inquiry_statuses`: category × code 一意。`StatusSeeder` が上表のステータス集合をそのまま投入。運用中に管理UI `Admin::InquiryStatusesController` から追加可） |
| ステータス選択＝通知トリガー | `InquiryRecipientRoute`（category × status_code → `RecipientGroup`）＋ `RecipientResolver.route_for` ＋ `InquiryNotifier` / `InquiryMessageMailJob`（Solid Queue） |
| アフター掲示板の分類・対応者 | `inquiries.after_urgency` / `after_type` / `after_area` / `reception_channel` / `first_responder_name` / `next_responder_name`（`05` §5-2 対応） |
| 投稿・添付 | `InquiryMessage`（Active Storage `has_many_attached :attachments`） |

過去データ（掲示板42万件）のアーカイブ投入は **R7**（`08`〜`10`）。

## 2. 顧客ステータスと「セットで必要な操作」

現行は**ステータス変更と同時に、掲示板記載・基本情報欄記載を手作業で行う**運用。

### 2-1. 新システムで自動化・強制すべき「セット操作」

現行が手作業でやっている「ステータス変更 → 掲示板記載 → 基本情報欄記載」は、
**新システムでは1つの操作にまとめ、記録漏れを機構的に防ぐ**べき。

| ステータス | セットで必要な記録（現行手作業） | 新システムでの自動化案 | brige-crm 状態（2026-08-19） |
|---|---|---|---|
| 不備チェック依頼 | 後確掲示板「再申請」＋確認コール詳細に不備解消記載 | 差戻し解消フォームから自動遷移＋履歴自動記録 | **R5 未実装**（契約ワークフロー状態機械） |
| 不備チェック不備返却 | 後確掲示板「営業部対応依頼」＋確認コール詳細記載 | 差戻し理由入力→通知→履歴（P3-6 → R5） | **R5 未実装**。通知経路（後確×営業部対応依頼→販売店）自体は R4 の `InquiryRecipientRoute` で表現可能 |
| 確認コール対応中 | 後確掲示板「対応中」＋架電履歴＋架電担当名 | 架電記録フォーム（担当は自動＝ログインユーザ） | 受け皿カラム `orders.confirm_call_*`（staff_name / time / notes / remarks 等）は **R2 実装済み**。遷移連動・担当自動セットは **R5 未実装** |
| 作業進行依頼 | 後確掲示板「後確OK」＋契約開始日＋契約書送付日入力 | ステータス遷移時に日付入力を必須化 | `orders.contract_start_date` / `contract_sent_at` は **R2 実装済み**。遷移条件化は **R5/R6 未実装**（04 R6「CustomerStatus/OrderStatus の遷移バリデーション」） |
| 作業進行中 | 発注日・アカウント発行日入力＋制作掲示板記載＋作業完了日 | 各日付を遷移条件に組込み（G-1: 商材別納品日） | `orders.issued_at` / `account_issued_at` / `work_completed_at` は **R2 実装済み**（`work_completed_at` は単一カラム。商材別分離 G-1 は 04 R6 で要否判断） |
| 完了 | 検収コールOK＋検収完了日＋計上月入力 | 完了遷移時に計上月を必須化 | `orders.inspection_call_completed_at` / `accounting_month` は **R2 実装済み**。必須化は **R5/R6 未実装** |

> 現行の最大の非効率＝**同じ情報を「ステータス」「掲示板」「基本情報備考」の3箇所に手で書く**こと。
> 新システムでは**1回の記録が全てに反映される**設計にする（`business-flow-analysis.md` 原則②と同根）。

### 2-2. ⚠️ ガルーンへの多重投稿（四重管理）— API連携で自動化を検討

現行では、上記3箇所に加えて**ガルーン（サイボウズ Garoon）にも同じ内容を投稿**している。
実務者MTGでも「システム内で完結せず、ガルーンで報告共有など手間が余計」「**ガルーンでの共有が
必須である業務フロー**となっている」と課題として挙がっている（`01` §2-2）。

つまり実態は**四重管理**（ステータス／掲示板／基本情報備考／ガルーン）。

**検討事項（CEO指示・2026-07-24）**

| 項目 | 内容 |
|---|---|
| 方針 | 新システムでの記録を、**ガルーンAPI連携で自動投稿**できないか検討する |
| 期待効果 | 手作業のガルーン転記を廃止し、四重管理を解消する |
| **必須の前提** | **情シス（情報システム室）への確認が必須**。ガルーンのAPI利用可否・認証方式・投稿先スペース/掲示板の指定・運用ポリシーを確認したうえで判断する |
| 技術メモ | サイボウズ(Garoon/Office)は REST API を提供。スペース/メッセージへの投稿が可能。連携先候補＝解約/キャンセル依頼スレッド（`ftcom.cybozu.com`。`06` §3） |
| リスク | ガルーン側の仕様変更・権限で連携が止まると業務が滞る。**代替として手動投稿も残せる設計**にする |

→ `development-plan.md` に **P4-25（ガルーン連携）** と **確認事項 Q-G2（情シス確認）** を追加済み
（Rails 版では 04 **R6「ガルーン連携」**。**未実装**・情シス確認も未着手）。
情シス確認は `release-readiness.md` G-2（情シスへのリスク連携）と併せて実施する。

## 3. ステータスの統廃合指針（浅賀さん精査）

精査表には**新システムで削除・統合すべきステータス**が明記されている。
旧Laravel側では `SampleDataSeeder` が現行の全ステータスを移植済みだったが、以下は**整理対象**。

> **brige-crm 実装状況（2026-08-19）**: Rails 版の `StatusSeeder`（`app/services/status_seeder.rb`）は
> `order_statuses` に **最小セット**（`0:受注`（`OrderStatus::CODE_ORDERED`・is_system）/ `10:作業進行中` / `21:解約` /
> `22:強制解約` / `100:CLOSE`）のみ投入し、現行37ステータス全件は移植していない（運用開始後に管理UI
> `Admin::OrderStatusesController` から追加する前提）。`customer_statuses` は Column.md §8 の申込ワークフロー
> 8件（applied〜withdrawn）。
> ✅ **2026-08-19 v5 CEO決定（DM-6）**: 精査結果は「受注（0）は不要・削除」だったが、**現状維持（`orders.status` 既定値 `"0:受注"` をそのまま新システムの正式な初期状態として使う）で決定**。実装変更・移行作業は不要。旧データの「受注(0)/空欄」は R7 移行時にこの初期状態へマップする。

| ステータス | 精査結果 | 対応 |
|---|---|---|
| 受注（0） | **不要**。インポート時は空欄で統一、受注ステータスは削除 | 削除候補 |
| 作業進行再依頼（9） | **不要**。「作業進行依頼」に統一 | 統合候補 |
| 対応・確認依頼（作業一旦停止）（11） | **不要**。「作業進行NG」に統一 | 統合候補 |
| 作業再開依頼（12） | **不要**。「作業進行依頼」に統一 | 統合候補 |
| 強制解約（不正）（95） | **不要**。該当案件が現時点0件のため削除 | 削除候補 |

> ⚠️ **移行との整合**：現行データ（案件3,298件）には統廃合対象ステータスの案件が存在し得る。
> **移行時にステータスのマッピング（旧→新）が必要**（`release-readiness.md` B-6 / `09` C-6 / `08` DM-6。**R7**）。

### 残すべきコア遷移（整理後のイメージ）

```
（空欄/受付）
  → 不備チェック依頼 ⇄ 不備チェック不備返却
    → 確認コール架電待ち ⇄ 確認コール不備返却 / 対応中 / NG / 済（保留）
      → 作業進行依頼 ⇄ 作業進行NG
        → 作業進行中
          → 検収確認コール依頼 ⇄ 検収確認コールNG / 対応中
            → 完了
（分岐）キャンセル / 解約 / 強制解約 / 解約処理待ち（月度別12） / CLOSE
```
