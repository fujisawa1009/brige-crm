## 2. 証拠の連鎖（何がどこまで確認できているか）

### 2-1. 会員IDは「加盟店側が発行」している

`決済カード登録APIフロー.xlsx` の図形注記（前任者の実装分析メモ）より：

- 現行フロー分析（drawing1）: 「**jutyu_cd 生成／member_id 生成／check_cd 生成** → POST
  `https://inet-uketsuke1.netmove.jp/cgi-bin/get_back.pl` → member_id にカード紐付け →
  ret_url へ返却 → **Jasmin へ転記/API連携（jutyu_cd / member_id）**」
- 新方式実装イメージ（drawing2）: 「加盟店システムで jutyu_cd 発行・member_id 発行/取得 →
  POST `/ec-payment-front/checkout` → カード有効性確認 → member_id に紐付け →
  ret_url 受信 → check_cd 検証 → member_id 確認 → 別システムへ転記」

導入ガイド 5.1.3 の `member_id` 定義（「**加盟店様が管理する顧客コード**」）とも一致。
→ **会員IDの名前空間は自社が握っている**。ネットムーブ側は「渡された member_id にカードを
ぶら下げる」だけ。これは移行にとって好材料（自社が同じIDを送り続ければよい）。

### 2-2. 実物の会員IDと受注コード（2026-05-19 テスト）

新CRMプロトタイプ（`crmsystem.jp`）の会員詳細画面キャプチャより：

| フィールド | 値 |
|---|---|
| ネットムーブ会員ID | **`60001864`（数字8桁）** |
| 受注コード | **`S084-6001864`（下位は数字7桁）** |
| カードブランド / カード変更日 | VISA / 2026-05-19 10:59:22 |
| 与信番号 | （空欄。フィールドだけ存在） |

> ⚠️ **「1桁」問題（決定者 の記憶どおり）**：会員ID `60001864`（8桁）と受注コード下位
> `6001864`（7桁）は**1桁ズレている**（3桁目の `0` が受注コードに無い）。
> 導入ガイドの受注コードは「サイトコード4桁＋**数字7桁**」なので、
> **8桁の会員IDは受注コードの下位にそのまま入らない**。
> 前任実装が「切り詰めた」のか「別採番」なのかは不明。
> - 切り詰めなら：会員IDが増えたとき**受注コードが衝突**する時限爆弾
> - 別採番なら：会員ID⇔受注コードの対応管理が別途必要
> → 依頼 D-5（新設）＋社内 S-3（前任ソースの確認）で確定させる。
> （Rails版）本論点＝04 **Q-37**（jutyu_cd 桁数）の一部。設計上は §6-3 のとおり **受注コード下位7桁を `SequenceCounter` の独立キーで採番**し、
> 会員IDとの一致に依存しないことで衝突リスクを回避済み（実装は R5）。

### 2-3. 新旧APIは同じ基盤を共有していると読める（＝引き継ぎに有利な材料）

1. **同一ホスト**：旧 `inet-uketsuke1.netmove.jp/cgi-bin/get_back.pl`、
   新 `inet-uketsuke1.netmove.jp/ec-payment-front/checkout`。ドメインもサーバも同じ。
2. **同一サイトコード**：旧画面のCSSパスが `images/S084/`、テストの受注コードが `S084-…`、
   管理画面ログインが `S084admin`。
3. **管理画面がひとつ**：USEN FinTech 管理画面に「会員一覧」「与信会員登録」があり、
   旧APIで登録した会員がここに見えている。新旧でストアが別なら管理画面も別になるはず。
4. **ガイド 2.2 の書きぶり**：「すでにご利用の加盟店様は **URLとパラメータが変更**となります」
   —— 会員の再登録が必要なら、この一文で済ませるはずがない。
5. **メールリンク決済のカスタマイズが新旧共通適用**（ガイド 2.3）＝設定も共有されている。

→ 状況証拠は「**同一サイト・同一会員ストアで、入口のAPIだけ変わる**」を強く示唆。
**ただし決め手（公式回答）が無い**。ここを依頼 B-3a で文書確認する。

### 2-4改.【解決】対応表はCRM内にあった（2026-07-27・顧客管理エクスポート精査）

決定者が現行ジャスミンCRMの**顧客管理画面**からDLしたCSV
（`private/ジャスミン資料/20260727_現行ジャスミンCRMからDL/`）に、
「**ネットムーブ会員ID**」「**ネットムーブ登録日**」列が存在した。§2-4 の懸念は解決。

| ファイル | 顧客数 | NM会員IDあり | 形式 | 重複 |
|---|---|---|---|---|
| all_user（BridgePlus） | 1,847 | **954（51%）** | 全件 **数字8桁・先頭「6」** | 0 |
| all_user_bridge（Bridge） | 1,115 | **438（39%）** | 同上 | 0 |

- 登録日の入力数が会員ID数と**完全一致**＝データ衛生は良好
- 両ファイル間の会員ID重複 0件（計1,392件がユニーク）
- **先頭が全件「6」**＝採番は「6＋7桁連番」の可能性が高い（1桁問題 §2-2 の有力仮説。
  リクリック質問■1で最終確認）

**クレカ案件を持つ顧客との突合（BridgePlus・案件CSV 2026-05-11断面と）**：

| 区分 | 人数 |
|---|---|
| クレカ払い案件を持つ顧客 | 980 |
| ├ NM会員IDあり | **928（95%）** |
| ├ NM会員IDなし | 52（**うち課金継続中とみられる 17人 ★要業務確認**） |
| └ 顧客CSV側に不在 | 0 |

→ **カバレッジ95%**。欠落は52人（課金中17人）に特定済みで、個別対応可能な規模。
　 欠落理由の候補：口振へ切替済み／登録前の新規／断面差（案件5/11 vs 顧客7/27）／データ漏れ。
　 → 17人のリストは必要ならCSVの顧客番号で抽出可能（`private/` 配下にのみ出力すること）。

**確定した移行方針**：`customers.netmove_member_id`（旧 `jasmin_customers.netmove_member_id`。決定Dによりモデル名は `Customer`）への取り込み元＝
**顧客管理エクスポート（またはDB再エクスポートの顧客テーブル）**。
「最新NM会員IDエクセル」の入手は**優先度低に格下げ**（このエクスポートと同源とみられる。
BWの月次運用の確認目的でのみ参照）。

### 2-4. 対応表の所在が最大の実務リスク（※上記 2-4改 で解決済み・経緯として保持）

- 現行ジャスミンのフィールド「**会員管理ID**」は形式 `英字1+数字9桁`（1,339件）で、
  **ネットムーブ会員ID（数字8桁）とは別物**（請求ポータル系のIDと推定。「請求パスワード」と併記）。
- ジャスミン仕様書（20251118）にも「ネットムーブ会員ID」に相当するフィールドは見当たらない。
- 一方、BW月次業務（`BridgePlusフロー_20260611.xlsx`）は課金作業に
  「**最新NM会員IDエクセル**」を使うと明記。

→ **顧客⇔ネットムーブ会員IDの対応表は、システム外のExcelにしか無い可能性が高い**。
これは B-3 の性質を変える：**ネットムーブが「引き継げます」と答えても、
「誰のカードがどの会員IDか」を新システムに正しく取り込めなければ同じことになる**。

Excel 由来ゆえの品質リスク：
- 網羅性（全クレカ顧客分あるか。手作業更新の漏れ）
- 一意性（1顧客に複数会員ID／使い回しが無いか）
- 鮮度（解約者・カード変更者の反映）
- 突合キー（Excel側の顧客特定が顧客番号か名前か。名寄せ問題 → `name-matching-process.md` の轍）

### 2-5. HMACキーは社内に既に存在する可能性が高い

2026-05-19 のテストは**実際にネットムーブの本番に到達し、与信 ok-01 が成立**している
（管理画面キャプチャに実取引あり）。つまり**その時点で有効な接続資材（サイトコード・
チェックコード生成に必要なキー等）を前任実装が保有していた**。

→ 「HMACキーをもらう」前に、**前任テスト実装の環境変数・設定ファイルから回収できる可能性**。
社内確認 S-3 の優先度を上げる。
※ 回収時の注意：キー現物の値を設計書・チャット等に**書き残さない**（認証情報の取り扱い規約）。
※（Rails版）回収した鍵の置き場は `Rails.application.credentials`（`config/credentials/*.yml.enc`）または ENV とし、
　 `Payment::Config`（`payment-integration.md` §4-9/§4-10）経由でサイトコード単位に取得する。リポジトリ・設計書には値を書かない。

## 3. シナリオ別の対応計画

### シナリオA：引き継がれる（本命・確度中〜高）

やることは「移行」ではなく「**取り込みと検証**」になる。

1. **最新NM会員IDエクセルを入手**し、`customers.netmove_member_id`（P2-4で新設済み＝Rails版 **R2 実装済み**・
   string(50)）へ取り込む ETL を作る（P5-5 移行計画に1タスク追加＝Rails版 **R7**。実装形＝rake タスク or `rails runner` スクリプト
   `lib/tasks/etl/netmove_member_ids.rake`（入力CSV → `customer_number` で `Customer` を引き `netmove_member_id` / `netmove_registered_at` を更新。
   検証レポート＝件数照合・重複・不一致を標準出力/CSVへ。**個人情報は `private/` 配下以外に出力しない**）
2. 品質検証：件数照合（クレカ払い顧客数と会員ID数）／重複検出／
   管理画面「会員一覧」CSVとの突合（依頼 H-1 のマニュアルで手段確認）
3. 疎通検証：既存会員ID 1件で `option=member-modify` を使った動作確認が安全にできるか
   ネットムーブに確認の上で実施（**勝手にやらない**。実顧客のカードに触る操作のため）
4. 新規申込は新API（checkout + member_id）で登録。**会員IDの採番規則を新旧で連続させるか
   切り替えるかを決める**（旧: 数字8桁 → 新も同形式が無難。string(50)なので余裕はある）
   （Rails版・R5）採番は `Payment::MemberIdAllocator`（`app/services/payment/`）に集約。既存顧客＝`customers.netmove_member_id` があればそれを返す／
   無ければ `SequenceCounter.next_value!("netmove_member_id")` で採番（キーの初期値は R7 の取り込み後に「既存最大値+1」へ**手動シード**し、
   新旧で衝突しないことを検証してから本番投入。`sequence_counters` テーブルは R2 実装済みで、初期値の設定は `SequenceCounter` レコードの `value` を
   直接更新すればよい）。**「6＋7桁連番」仮説（§2-4改）が確定するまで採番形式は確定させない**

### シナリオB：引き継がれない（保険・確度低）

**約400件+Bridge分の再登録キャンペーン**が必要になる。設計要素：

1. **手段はガイドが用意している**：「**メールリンク決済**」（ガイド2.3）＝管理画面から
   決済URLをメール送信 → 顧客がカード入力。**再登録導線を自社開発しなくてよい**可能性
   （Rails版）自社開発する場合の候補＝顧客マイページ（`Mypage::CardsController`。Devise Customer + メールOTP。R4 で最小構成のマイページ実装済み）
   から `option=member-modify` 付き checkout へ遷移させる導線。`payment-integration.md` §4-10「カード変更導線」と同一機構で作れる
2. ただし P-N1（メールリンク決済で金額・商品名が顧客に見える疑い）が未解決のまま使うと
   「月額を顧客に見せない」方針と衝突 → 依頼 J-1 の回答が前提
3. 未登録のまま請求日を迎える顧客の扱い（口座振替への一時切替？請求書払い？）＝business 側の判断
4. 段階実施（請求月の分散）と、再登録率のモニタリング
5. **解約誘発リスク**を決定者に事前共有（カード再入力は解約のきっかけになり得る）

### どちらでも共通で必要なこと

- `customers.netmove_member_id` への取り込み（対応表の内製化。カラムは R2 実装済み・ETL は R7）。
  **シナリオAでもBでも、Excel運用をシステムに吸収するのがゴール**
- 会員IDと受注コードの関係の確定（§2-2 の1桁問題）
- カード変更（有効期限切れ・再発行）の導線：`option=member-modify` で
  既存会員IDのカードを差し替えられる（ガイド5.1.3）。**洗替の自動連携があるかは別途**（依頼 A-6）
  （Rails版・R5）導線の section は未決（`payment-integration.md` §4-10: 候補A＝mypage で顧客本人が再 checkout／候補B＝admin からメールリンク決済案内）。

## 6. 実装への反映（確定を待たずにやってよいこと）

> Rails版（2026-08-19）: 各項目の実装形とフェーズを併記。いずれも **未実装**。

1. `netmove_member_id` の取り込みETLの**枠だけ**用意（P5-5 に追記＝Rails版 **R7**。入力＝Excel/CSV、検証レポート付き）

   　 R5 では「`customers.netmove_member_id` が既に埋まっている顧客は採番しない」というインターフェースだけ `Payment::MemberIdAllocator` に固定しておく

   （既存顧客は取り込んだIDを使い、新規は採番。採番形式は D-5/S-3 の回答で確定）
   → **R5** `app/services/payment/member_id_allocator.rb`。`SequenceCounter`（R2 実装済み・PostgreSQL 単一UPSERTでアトミック）を利用。
   　 `customers.netmove_member_id` に unique index が無い（R2 現行 schema）ため、採番導入時に **部分ユニークインデックス
   　 `WHERE netmove_member_id IS NOT NULL` の追加**を R5 migration に含める（要確認: 旧データ取り込み時に重複が無いことは §2-4改 で確認済み＝0件）
3. 受注コード採番を**会員IDから独立**させる（§2-2 の衝突リスクを設計で回避。
   `jutyu_cd` 下位7桁は自前のシーケンスとし、会員IDとの一致に依存しない）
   → **R5** `app/services/payment/jutyu_code_generator.rb`: `"#{site_code}-#{format('%07d', SequenceCounter.next_value!("netmove_jutyu_cd_#{site_code}"))}"`
   　（ハイフン有無・12文字前提は 04 Q-37 の確定待ち。`payment_transactions.jutyu_cd` の unique index が二重採番の最終防壁）
4. カード変更導線（member-modify での再 checkout）を P3-2 のスコープ境界に明記
   （実装は後続。データの置き場所＝`card_brand`/`card_last4`/`カード変更日` 相当は
   `payment_transactions` 側にあるため追加カラム不要の見込み）
   → **R5 スコープ境界として明記のみ**（実装は S-7新の回答後）。section 候補は §3「共通」参照
5. （Rails版追加）`Customer` の `Auditable` TRACKED_FIELDS に `netmove_member_id` / `netmove_registered_at` を追加する

   　 会員IDの変更履歴が監査ログに残らない。ETL 取り込み・採番・手修正のいずれも証跡が要るため **R5 の migration と同時に追加**（値は秘匿値ではないので記録可）
